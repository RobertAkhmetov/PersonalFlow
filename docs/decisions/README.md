# Architecture decision records

Use an ADR when a choice has long-lived consequences for platforms, API boundaries, sync, security, storage, or deployment. An ADR records rationale and trade-offs; it does not replace the detailed product or architecture specification.

## Status and editing

- New alternatives begin as Proposed.
- Explicitly accepted directions are Accepted.
- Replaced records become Superseded and link to the replacement.
- Preserve historical records; update the canonical specification when behavior changes.

Each ADR uses: Context, Decision, Consequences, Status, and Date.
